# Redline Closure Loop

本模块用于把重大问题从“识别风险”推进到“事实确认、成套红线、修订证据复核、修改后风险扫描和签署稿终检”。它是通用判断指南；不得把单一事项的事实、让步或处理结果写成其他事项的默认答案。

## 1. 适用范围与核心区分

以下任一情形必须执行本闭环：

- 用户要求直接制作红线稿；
- 需要把 Skill 问题清单与律师稿、对方稿或其他修订稿逐项比较；
- 已接受一轮修改，需要检查清洁稿或签署稿；
- 一个修改可能影响多个条款、多个文件或另一项控制机制。

回应分级是**诊断工具**，只说明修订文本在多大程度上处理了原始关切。它与以下两个判断相互独立：

- 谈判状态：例如 Accepted / 已接受、Rejected / 已拒绝、Partially Accepted / 部分接受；
- 法律与文本质量：例如修改是否有效、可执行、商业上适当、符合客户授权或足以签署。

因此，`Complete / 完全回应` 不等于对方已接受，也不证明法律正确；`Alternative Solution / 替代方案回应` 也不等于该替代方案应被采纳。

## 2. 场景到阶段映射

五个阶段是核心工作流第7、14和16步中的**条件式判断子程序**，不是五个
新的 `review_checkpoint.py` 阶段，也不改变现有16步检查点。只执行当前场景
需要的阶段；不得把五个阶段机械串联为每次任务的固定顺序。

| 阶段 | 核心问题 | 必须留下的证据 |
|---|---|---|
| 一 | 哪些事实决定能否选定文本？ | 最少事实问题、来源、未答变量和假设边界 |
| 二 | 重大问题需要哪一档完整机制？ | 首选、平衡、最低可接受文本；不适用时说明原因 |
| 三 | 哪些条款和文件必须同步？ | 条款/文件清单、依赖方向、核验状态 |
| 四 | 修订稿实际回应到什么程度？ | 原始关切、可定位修订证据、回应等级、剩余/新增风险、下一步 |
| 五 | 修改是否产生变异，终稿是否可签？ | 有可识别修改时的变异扫描记录；清洁稿/签署稿在本轮范围内时的终检记录 |

按场景路由如下：

| 场景 | 必须执行的阶段 | 边界 |
|---|---|---|
| 首次按请求制作红线 | 阶段一至三；实施红线后立即执行阶段五第5.1节修改后变异扫描；如继续形成清洁稿/签署稿，再执行第5.2节 | 没有既有问题与他人修订稿的比较时，不执行阶段四，不虚构回应等级 |
| 比较问题清单与律师稿/对方稿 | 有既有问题或立场基线时执行阶段四，并将未解决、重新开启、新增问题及替代方案的剩余风险返回阶段一至三；只要修订标记或版本比较能够识别修改，无论是否有问题清单，都执行阶段五第5.1节，若又实施修改则再次扫描；清洁稿/签署稿在本轮范围内时再执行第5.2节 | 缺少问题/立场基线时不给回应等级，但不因此跳过可识别修改的第5.1节扫描 |
| 清洁稿或签署稿复核 | 最终清洁稿/签署稿在本轮范围内时执行阶段五第5.2节；存在可识别修改或版本比较时同时执行第5.1节；发现新的、重新开启或未完成的问题时返回阶段一至三 | 只有同时存在既有问题/立场和可定位修订证据时，才另行使用阶段四；没有在范围内的最终版本时不虚构第5.2节终检 |

确认插入点：首次实质红线在阶段一至三形成拟议方案后、实施修改前进入
`references/lawyer-confirmation-gate.md`；律师确认后才实施，并立即执行第5.1节。
变异扫描若新增问题或改变已批准分析/文本，回到新确认批次并保留 supersedes；
方向性意见和 `LAWYER-NEW` 在回读完成前不得进入最终红线。

阶段五第5.1节的修改后变异扫描属于独立风险复核，不属于阶段四的回应分级。
回应矩阵不能替代全文变异扫描，全文变异扫描也不能自动生成回应等级。

两个前提必须解耦：

- **阶段四回应分级**要求既有问题清单或其他可证明的既有立场基线；
- **阶段五第5.1节修改后变异扫描**要求可识别的修订标记、两版文本比较
  或本轮实际实施的编辑，不要求既有问题清单。只要修改可识别，即使缺少
  回应分级基线，也必须扫描修改后全文和关联文件。

## 3. 阶段一：最少事实依赖问题

### 3.1 提问原则

只询问会改变建议机制、义务主体、审批路径、履行可行性或风险分配的事实。可以从协议正文、披露材料或用户指令可靠确认的，不重复询问。

每个重大问题至少记录：

1. **决策变量**：哪个未知事实会改变文本；
2. **最少问题**：取得可执行答案所需的最短问题；
3. **证据来源**：正文、配套文件、用户确认或待核验；
4. **未答处理**：使用方括号变量、并列方案或暂缓结论；
5. **禁止假设**：不得代替客户确定商业让步、主体能力或外部可行性。

### 3.2 最少问题模板

```markdown
- 决策变量：
- 最少事实问题：
- 已有证据及定位：
- 未获回答时的方括号变量/并列方案：
- 哪一项结论必须暂缓：
```

如果答案只影响表述细节，不影响风险分配，可先以变量完成文本；如果答案决定交易路径是否可行，应先标记为待确认，不把一个路径写成既定事实。

## 4. 阶段二：重大问题三档成套文本

### 4.1 三档语义

- **首选方案 / Preferred**：完整实现客户目标，并处理已识别的主要依赖和执行风险。
- **平衡方案 / Balanced**：保留核心保护，同时缩窄触发、主体、程序或救济以提高可谈判性。
- **最低可接受方案 / Minimum Acceptable**：只保留不得丢失的底线机制，并明确仍然存在的剩余风险。

三档必须是可直接放入文件的完整机制，而不是“加强保护”“适当缩小”等原则性提示。每档应覆盖适用的触发、主体、程序、期限变量、通知、救济、例外、终止后存续和跨文件优先顺序。

### 4.2 何时不机械提供三档

三档仅在重大问题且存在真实可谈判区间时提供。以下情形可以不提供三档，但必须说明原因：

- 强制性要求或客观可行性只有一个合规路径；
- 纯定义、条号、交叉引用或签署页清理；
- 事实不足导致任何一档都无法负责任地选定；
- 不同方案并非强弱关系，而是互斥的交易路径。

互斥路径应并列为“方案甲/方案乙”，分别列明事实前提和剩余风险，不得错误包装成强弱档。

### 4.3 三档输出模板

```markdown
- 首选方案：完整条款或完整修改指令
- 平衡方案：完整条款或完整修改指令
- 最低可接受方案：完整条款或完整修改指令
- 各档共同依赖的事实：
- 各档差异及剩余风险：
```

## 5. 阶段三：同步条款与文件清单

### 5.1 同步检查方法

对每个重大问题先画出“触发—权利/义务—程序—救济—终止/存续”的机制链，再检查每一环出现在哪些定义、正文、附件、章程、批准文件、披露文件或其他交易文件中。

同步清单至少记录：

| 同步对象 | 依赖关系 | 所需动作 | 核验状态 |
|---|---|---|---|
| 定义或解释条款 | 为机制提供统一口径 | 新增/修改/删除 | 已核验/待核验/不适用 |
| 操作条款 | 建立触发、程序和履行路径 | 成套修改 | 已核验/待核验/不适用 |
| 关联权利或救济 | 防止重复、冲突或落空 | 协调优先顺序与排他性 | 已核验/待核验/不适用 |
| 配套文件 | 使批准、登记、交割或治理安排一致 | 同步修改或列为交付物 | 已核验/待核验/缺文件 |
| 终止与存续 | 确认历史义务和持续义务 | 明确释放、保留或继续承担 | 已核验/待核验/不适用 |

如果某项没有关联条款或文件，明确写 `not applicable / 不适用`，不得留空。

## 6. 阶段四：基于证据的回应分级

### 6.1 七级语义合同

| English | 中文 | 判断标准 |
|---|---|---|
| Complete | 完全回应 | 原始关切的全部实质要素均有可定位修订证据，未发现重要剩余风险 |
| Substantial | 实质回应 | 核心保护已落地，仅有非核心缺口或可管理的剩余风险 |
| Partial | 部分回应 | 修订触及问题，但仍缺少重要要素、依赖或执行机制 |
| Alternative Solution | 替代方案回应 | 未采用首选写法，但以不同机制实质处理原始关切；仍须独立评估剩余风险 |
| Unaddressed | 未回应 | 没有可定位的实质修订或回复证据 |
| Reopened | 重新开启 | 先前已解决或已关闭的关切在本轮文本或关联文件中再次出现 |
| New Issue | 新增问题 | 修订产生或暴露不属于原始关切范围的新风险；使用新的 `NEW-` 编号 |

### 6.2 证据规则

每个等级都必须以当前修订稿、关联文件或明确回复为证据，并给出可复核定位。文本相似度、篇幅变化或仅有修订痕迹都不是充分证据。

逐项记录七个字段：

1. Issue ID / 问题编号；
2. Original Concern / 原始关切；
3. Revision Evidence / 修订证据；
4. Response Status / 回应状态；
5. Residual / New Risk / 剩余/新增风险；
6. Synchronized Clauses / 同步条款；
7. Next Step / 下一步。

七个字段均不得留空。确无剩余风险或同步条款时填写 `not applicable / 不适用`。回应矩阵完成后运行：

```bash
python3 scripts/validate_response_matrix.py path/to/response-matrix.csv
```

该校验只证明结构、允许状态和证据字段完整，不证明回应等级判断正确。

## 7. 阶段五：修改后变异扫描与清洁稿终检

### 5.1 修改后变异扫描

完成红线或评估修订稿后，必须从修改后的全文重新扫描，而不是只复读修订段落：

- 原机制被删除后，是否以另一项直接控制、同意、否决或救济重新出现；
- 修改是否改变义务主体、触发条件、责任顺序、上限、损失范围或终止后存续；
- 定义、例外、附件或关联文件是否使新文本落空；
- 一个问题的解决是否削弱另一项权利，造成重复救济或产生执行冲突；
- 是否需要把原 Issue 标记为 `Reopened / 重新开启`，或另建 `New Issue / 新增问题`。

### 5.2 清洁稿与签署稿终检

接受修订并生成清洁稿后，逐项检查：

- 定义已使用、用语一致，删除条款对应的定义和引用已清理；
- 条号连续，附件、附表和标题编号一致；
- 交叉引用指向现存且正确的条款或附件；
- 交易金额、币种、单价、股数/注册资本、持股比例、估值、责任上限、
  表决门槛、公式参数和附件合计在全文及关联文件中一致；
- 文件签署、生效、交割、付款、长期截止、通知、报告及其他履行日期
  与期间前后一致，不存在过期占位、冲突时序或误留的旧版本日期；
- 方括号、修订标记、批注、占位符和删除残留已处理；
- 签署页主体、签署身份、签署栏、附件签署安排和文本中的当事方口径一致；
- 主协议、治理文件、批准文件和其他同步文件反映同一机制；
- 最终文件与已批准的方案一致，未在清洁过程中发生无记录变动。

发现问题时回到相应阶段修正，并重新执行变异扫描和终检。一次通过红线比较不等于可以签署。

## 8. 通用依赖示例

### 8.1 可转换工具的转换、终止、担保与历史释放

审查可转换票据或 SAFE 时，不只看转换公式。先确认未转换工具、转换触发、终止时点、担保或增信是否继续、历史违约与权利是否释放，以及转换后证券文件是否承接原义务。同步检查定义、资本结构、交割文件、终止条款、担保文件和释放条款。

### 8.2 主体整合的可行性、税务、配合和时间

要求业务或资产整合到指定主体时，先问整合对象、权属、许可、第三方同意、税务影响、各方配合义务和可实现时序。事实不足时使用变量或并列路径，不把“应当整合”当作已经可实施。

### 8.3 跨境治理分配

跨境结构中，明确境内运营主体、境外控股层和协议控制层分别由谁批准、谁任命、谁执行，以及各层治理文件是否一致。不得仅在一份股东协议中写控制权，而忽略章程、董事会规则、授权文件或协议控制文件。

### 8.4 ESOP 与员工/顾问现金补偿的审批边界

区分股权激励池、具体授予、员工现金薪酬、顾问费用和特殊奖励。明确哪些事项进入股东、董事会、投资人或薪酬委员会批准，哪些属于经批准预算内的日常经营，避免把普通雇佣决策意外纳入投资人逐项同意。

### 8.5 删除董事席位但增加直接同意权

删除董事席位可能降低形式上的治理参与，但若同时新增投资人直接同意权，原控制关切可能以不同机制重现。应分别评估董事权利的删除、直接同意权的范围、触发门槛、期限、监管影响和与保留事项的重叠，并可能同时记录 `Alternative Solution / 替代方案回应` 与新的剩余风险。

### 8.6 赔偿顺序、上限与损失定义

赔偿机制应同步处理责任来源、责任主体、追偿顺序、存续、门槛、上限、可赔损失定义、减损、保险或第三方追偿以及避免重复获偿。只修改上限而不检查损失范围和责任顺序，通常不足以关闭问题。

### 8.7 清洁稿中的定义、数值、编号、交叉引用与签署

删除或替换操作条款后，检查相关定义是否仍需保留，交易金额、日期及其他数值是否在正文、附件和关联文件中一致，编号是否连续，交叉引用是否仍指向正确机制，附件是否同步，以及签署页是否覆盖全部应承担义务的主体。纯形式错误或数值冲突也可能使成套机制无法执行或造成解释争议。

## 9. 完成标准与常见误判

闭环完成只要求**本次场景实际路由到的证据**全部齐备：

- 路由到阶段一至三时，事实依赖已回答或明确保留变量，适用的重大问题
  已有成套文本，同步清单已核验；
- 只有路由到阶段四时才要求有证据的回应矩阵；没有既有问题/立场基线时，
  回应矩阵不适用且不得作为完成条件；
- 只有存在可识别编辑或版本比较、因而路由到阶段五第5.1节时，才要求修改
  后变异扫描记录；该扫描不以既有问题清单为前提；
- 只有最终清洁稿或签署稿在本轮范围内、因而路由到阶段五第5.2节时，才
  要求清洁稿/签署稿终检记录。

不适用的阶段证据不得被虚构，也不得阻止一个范围清晰的有限任务按限制条件完成。

常见误判包括：

- 把文字变短当作风险降低；
- 把采用不同写法当作未回应；
- 把回应分级当作谈判接受状态；
- 把 `Complete / 完全回应` 当作法律质量证明；
- 只检查修改段落，不扫描修改后全文；
- 只修改主协议，不核验定义、章程、批准文件、附件和签署页；
- 在事实未确认时替客户选择履行主体或交易路径。
